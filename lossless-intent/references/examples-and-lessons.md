# 案例与经验

以下内容来自本次讨论中的两组需求测试与后续 Skill 设计确认，只用于提炼协作规则。它们不是部署本 Skill 后的独立模型评测，也不是市场需求或技术实现证据。虚构小样中的数据不代表实际文件或本机状态。

## 案例一：PPT 整合的两个结果

用户初始需求：整合两个或多个 PPT，并探索其他有价值的功能。

讨论中逐渐明确：统一交付为主，智能整理为辅；允许优化文字与结构，再由用户检查。AI 展示“保留原有章节”和“按汇报目的重组”两个小样，并询问偏好的默认结果。

用户关键反馈：

> 我两个结果都要，作为选项，让用户自己选择。

正确共识：两种能力都提供，默认选什么尚未确定。部门月报只是沟通示例，不限定所有使用场景。

提炼的规则：产品能力集合、默认值和一次任务选择不是同一个问题。范例用来暴露分歧，不能把兼容能力强制变成二选一。确认方向不等于批准此前列出的全部候选功能。

## 案例二：本地 Skill 管理

用户初始需求：网页版管理本地 Skill，能安装、统计使用情况、卸载和自定义改造。

三次关键反馈：

> 所有的AI工具，系统可以自动搜索本地的所有Skill.

> 一起更新

随后认可：卸载时选择安装范围、支持全选、默认保留原始下载文件。

正确共识：覆盖所有工具是需求目标，尚非实现证据；关联版本可以一起更新，卸载范围仍可选择。不能把更新联动扩展为删除联动。

仍有关键缺口：“一起更新”没有说明不同版本已有改动如何处理；使用统计口径和自定义改造体验没有完整展开。找到文件不等于已安装，没有日志不等于零次使用。

提炼的规则：先看整体使用过程，再深入关键分歧。短回答后检查重要剩余解释；只有新的关键歧义才提问，不重问已回答内容。三轮结束不等于所有需求已完整对齐。

## 一次正确的整体交互小样

### 输入

“做个产品介绍页，要高级、简洁，让普通人看懂。”

### 第一次回应

我理解的目标是：普通访客看懂用途，并知道如何开始使用。

整体小样：产品演示 → 解决的问题 → 使用效果 → 使用入口。

暂时假设：先展示产品比先读长介绍更合适。本轮只判断信息顺序，不确认配色，也不证明功能已经具备。

关键判断：这个整体顺序是否接近？可以只指出最不对的地方。

### 用户反馈

“演示在前没问题，但不要视频，希望用户能直接试。”

### 更新

保留：产品在前，说明简短。

修正：演示指可操作体验，不是视频。

未定：具体开放哪些功能，以及当前真实能力。只有它影响制作范围时，才围绕这一点继续，不重问信息顺序。

### 收敛及交接

整体回放：访客先体验一个确认过的核心功能，再阅读用途与效果，最后进入正式使用。

保留当前共识及关键限定，列出真实未验证项。已有制作授权则继续，不额外要求用户再批准一次“开始”。

## 高频反例

| 不合适的处理 | 更合适的处理 |
|---|---|
| 把“高级、简单”换成“高端、简约”再问是否正确 | 用内容、布局或操作小样展示具体解释 |
| 每个任务先问十二个问题 | 根据材料先给整体小样，只检查一个主要分歧 |
| 用户认可配色就开始上线 | 配色认可只记录配色；发布仍受操作授权约束 |
| 两个模式都要，于是擅自默认第一种 | 记录两种能力，默认项保持未定 |
| 没有日志，显示调用次数 0 | 区分未记录、统计范围和真实未知 |
| 用户无法判断技术，就替他宣布安全 | 用可核对的功能证据验证，未知标明 |
| 需求已经明确，做错了还让用户再解释 | 检查执行失败并修复 |
| 已确认需求在手仍要求重新来三轮 | 复用共识，按当前状态继续 |

## 从经验到规则的限制

用户在看到小样后可能改变主意，也可能发现 AI 误解；不能一概视作“成功还原最初意图”。用户回复短也不能证明总阅读负担低。没有独立对照和真实执行结果，就不报告理解准确率、返工节省比例或全工具兼容性。
