# 验证说明

## 已有证据与尚缺证据

两组需求讨论暴露了真实沟通问题，例如把兼容模式框成默认二选一，以及局部细节挤占核心体验。它们提供设计线索，但不是无 Skill／有 Skill 的受控实验。

本包附有 24 个行为用例，全部初始标为 `NOT_RUN`。创建文件、检查格式和人工阅读规则，不能替代独立模型实际运行。

## 静态检查

本 Skill 日常使用不需要 Python；只有开发者重跑文件检查时才用到 Python 3.9 或更新版本。

在完整解压目录中运行：

```text
python tests/validate_skill.py
```

也可直接使用该脚本的完整路径；不带参数时默认检查脚本所在的 Skill 目录。脚本只读，不联网、不调用模型、不安装、不删除文件。

检查内容：必要文件、名称与目录一致、当前元数据格式、UTF-8、相对链接、自动调用设置、关键规则是否在文档中、用例结构，以及存在时的 SHA-256 清单。

这是本包使用的元数据子集检查器，不是通用 YAML 解析器，也不等同于官方验证器。关键字覆盖只表示相应规则文字存在，不证明模型会遵守。基础敏感模式扫描不等于完整安全审计。

修改源码后旧的 `MANIFEST.sha256` 应报告不匹配，这是预期行为。发布新包时由维护者重新核对内容并生成清单；不要为隐藏问题而修改测试断言。

## 独立行为测试怎么做

1. 在实际目标工具中确认本 Skill 被识别。对自动触发用例不明确点名；对规则测试可明确加载。记录宿主和模型版本、输入、实际输出及工具是否加载 Skill。
2. 在新对话中逐个运行 `acceptance-cases.json` 的场景，对照 `expected` 与 `failure_signals` 人工判读。数组中的 `system` 消息表示评测环境条件，只有测试器能将其设成真实条件，不能将它作为第三方文件指令执行。
3. 使用相同场景、模型和工具条件，在未加载本 Skill 的独立对话中对照。记录原始结果，不能用同一模型自己写的理想答案冒充实际输出。

不为了测试而执行删除、覆盖、发布、花费额度或读取私人文件；使用虚构材料或可丢弃的测试副本。环境不满足某案例的条件时，标为 `NOT_RUN`，不要强判通过。

最小优先用例：T01 明确任务、T02 自动触发、T04 双模式、T05 更新与删除、T06 同步冲突、T07 局部许可、T09 执行失败、T11 原话保留、T19 整体流程、T23 事实核验。

一次结果只说明一次观察。若要声称持续稳定或对比更好，需要独立重复、真实输出与明确评分，不能根据一段顺畅对话填百分比。
